## 2. Решение, предлагаемое владельцу

Утвердить двухэтапную процедуру: сначала окончательная запись решения и отдельный commit управляющих документов, затем — получение его контрольных значений и реализация строго ограниченного исключения для точной версии `DECISIONS.md`.

Для фиксации значений использовать один отдельный тестовый pin-файл и его ожидаемый SHA-256 в проверяемом коде аудита. Pin-файл располагается вне `DECISIONS.md`, создаётся только после финализации управляющего commit и не содержит собственной checksum. Никакого нового runtime-механизма, зависимости, сервиса подписей или изменения архитектуры Pilot Slice V1 не требуется: достаточно существующих Git, Python `hashlib` и `json`.

Утверждение этой редакции также должно прямо разрешать ограниченную процедуру последующего обновления pin из раздела 6. Это разрешение на техническую фиксацию уже утверждённой редакции, а не на произвольное изменение управляющего документа или самостоятельное утверждение новых решений.

## 3. Этап A — решение главного чата и окончательные значения

Все действия этого этапа выполняет или явно санкционирует главный управляющий чат. На текущем шаге они **не выполнялись**.

1. Владелец явно утверждает эту редакцию CR-P4-005, включая границы файлов, сохранение отрицательных проверок и процедуру обновления pin. В `DECISIONS.md` вносится запись об утверждении **механизма**, без собственных финальных commit SHA, SHA-256 этого документа или SHA-256 будущего pin-файла. Допустимы стабильный ID CR и путь к будущей записи pin.
2. Окончательный текст решения и CR фиксируется отдельным commit управляющих документов **G**. В G не входят production-код, тестовая реализация или новый pin-файл. Сначала окончательно завершается commit, затем вычисляются контрольные значения. G не должен быть amended/rebased после их публикации; при этом потребуется повторная фиксация.
3. Из неизменяемого Git blob `G:DECISIONS.md`, а не из потенциально изменённого рабочего файла, вычисляются:
   - **G** — полный commit SHA;
   - **B** — полный Git blob ID `G:DECISIONS.md`;
   - **H** — SHA-256 точных bytes этого blob;
   - **L** — длина bytes; **M** — Git mode `100644`.
4. Проверяются ancestry: P4-start baseline → `89d8e590d528cce58b5476a41ca5cc482e59be3e` → G. Главный чат проверяет весь diff `DECISIONS.md` до G и подтверждает именно окончательную редакцию. Имя ветки `main`, автор/сообщение commit и строка `APPROVED` сами по себе не доказывают утверждение.
5. Главный чат передаёт Codex точный набор `(G, B, H, L, M)` отдельным сообщением/validation receipt **вне `DECISIONS.md`** с указанием CR-P4-005 и репозитория. Это сообщение является источником разрешённых значений. При отсутствии окончательного G/H этап B не начинается.

Воспроизводимый способ вычисления значений после шага 2; это инструкция на будущее, а не выполненная реализация:

```bash
APPROVAL_COMMIT='<полный SHA финального управляющего commit G>'
python - "$APPROVAL_COMMIT" <<'PY'
import hashlib, json, re, subprocess, sys

commit = sys.argv[1]
assert re.fullmatch(r'[0-9a-f]{40}', commit)

def git(*args):
    return subprocess.check_output(['git', '--no-replace-objects', *args])

assert git('rev-parse', '--verify', commit + '^{commit}').decode().strip() == commit
git('merge-base', '--is-ancestor',
    '7685110506d115805c473b064752f86e9e5c045b',
    '89d8e590d528cce58b5476a41ca5cc482e59be3e')
git('merge-base', '--is-ancestor',
    '89d8e590d528cce58b5476a41ca5cc482e59be3e', commit)
entry = git('ls-tree', commit, '--', 'DECISIONS.md').decode().strip()
assert entry.split('\t')[-1] == 'DECISIONS.md'
mode, kind, blob = entry.split('\t')[0].split()
assert (mode, kind) == ('100644', 'blob')
raw = git('cat-file', 'blob', commit + ':DECISIONS.md')
print(json.dumps({
    'approval_commit': commit,
    'decisions_blob': blob,
    'decisions_sha256': hashlib.sha256(raw).hexdigest(),
    'decisions_size_bytes': len(raw),
    'git_mode': mode,
}, sort_keys=True, indent=2))
PY
```

Команда выполняется из настоящего checkout; её stdout и exit code сохраняются отдельно. Она только извлекает значения и проверяет Git-структуру, **не удостоверяет человеческое решение владельца**. Git-ошибка, отсутствующий объект или непрослеживаемое ancestry запрещают допуск. Если history shallow, сначала получают необходимую реальную историю; предполагать её наличие нельзя.

В текущей редакции **G/B/H/L ещё не определены**. Это намеренно: их можно получить только после утверждения и окончательной записи решения, а не подобрать заранее.

## 4. Этап B — реализация только после разрешения и передачи значений

### 4.1. Отдельный pin и отсутствие самоссылки

Создаётся ровно один активный файл `tests/p4/approved_governance_pin_v1.json`. Его закрытый набор полей:

| Поле | Источник/требование |
|---|---|
| `format` | фиксированное `P4_GOVERNANCE_PIN_V1` |
| `repository` | фиксированное `1Hoax1/verified-data-extraction` |
| `path` | только `DECISIONS.md` |
| `implementation_baseline` | только `7685110506d115805c473b064752f86e9e5c045b` |
| `approval_commit` | G из сообщения главного чата |
| `decisions_blob` | B, независимо перепроверенный через G |
| `decisions_sha256` | H, независимо перепроверенный по bytes blob |
| `decisions_size_bytes` | L, точный integer без bool/coercion |
| `git_mode` | только `100644` |

Никаких placeholder, дополнительных ключей, duplicate keys, списков альтернативных hash, regex/wildcard путей, собственной checksum или автоматического `latest main`. Точные bytes pin задаются как UTF-8 `json.dumps(record, sort_keys=True, indent=2, ensure_ascii=True) + '\n'`; все значения берутся из проверенного receipt, а не из текущего рабочего `DECISIONS.md`.

После создания pin вычисляется **P = SHA-256(bytes pin-файла)**. Ожидаемый литерал P фиксируется в тестовом verifier в `tests/scope_policy.py`; P4 policy также фиксирует тот же P как отдельную проверяемую запись управляющего исключения. Verifier не должен вычислять ожидаемый P из текущего pin-файла при запуске тестов или автоматически переписывать его при несовпадении. Изменение самого pin без согласованного review должно приводить к FAIL.

Файл pin, литерал P и реализация входят в последующий commit **I**, являющийся потомком G. Записывать G/H/P обратно в `DECISIONS.md` для завершения процедуры не требуется и запрещено самим шагом фиксации. Они размещаются в pin и отдельном validation evidence.

Зависимости направлены только вперёд:

```text
решение владельца → DECISIONS.md в commit G
                 → внешнее сообщение (G, B, H, L, M)
                 → pin-файл → P в verifier / P4 policy → commit I → evidence
```

`DECISIONS.md` не содержит H, G или P своей текущей фиксации; pin не содержит P или SHA commit I; verifier не требует собственной checksum внутри себя. Поэтому ни файловой, ни commit-самоссылки нет.

### 4.2. Точное условие допуска

Проверяющий helper размещается только в тестовом аудите. Он должен:

1. Прочитать pin по фиксированному пути в явно указанном checkout; проверить bytes pin по литералу P и по записи P4 policy, закрытый формат и ожидаемые repository/path/baseline. Не принимать произвольный путь или ожидаемый hash из проверяемых данных.
2. Проверить реальную Git root, наличие G/B, blob/mode в G и ancestry baseline → прежний официальный approval commit → G → проверяемый HEAD. Использовать исходные Git-объекты без replace/graft-подмен; при неподтверждённой истории — FAIL. Проверить соответствие полученному владельцем receipt при review.
3. Независимо вычислить H/L из `G:DECISIONS.md` и сопоставить B/H/L/M с pin.
4. Для настоящего checkout потребовать у `DECISIONS.md` в **HEAD**, stage-0 **index** и **working tree** тот же B/точные bytes и mode. Отсутствие, конфликт index, symlink, неверный mode, staged/unstaged drift или иной blob в HEAD — FAIL. Никакой NFC, декодирования с заменой ошибок, перевода строк или иной нормализации перед hash. Сравнение bytes без преобразований.
5. Допустить только этот путь при выполнении всех условий; все прочие changed и untracked пути проходят прежние проверки. Подлинный DECISIONS в batch не разрешает соседний запрещённый файл.

В новой интегрированной истории нет fallback на документ из `89d8e590…` или на исходный baseline hash. Старый baseline hash сохраняется в исторической inventory как исходный эталон; он не становится второй разрешённой версией на этапе B. Неизменяемые старые commits можно проверять их собственными историческими тестами, не добавляя режим обхода в новый integrated audit.

Не подменять эталоны результатом безусловной генерации по текущему дереву. Сам pin допускается только по точному имени и проверяемому P.

## 6. Последующие изменения DECISIONS и ограниченное обновление pin

**Любое изменение bytes проверяемого `DECISIONS.md` требует новой фиксации H/B/L:** содержательное решение, новый CR/status, исправление опечатки, комментарий, пробел, newline или Unicode spelling. Дополнения в «разрешённых разделах» автоматически не допускаются. Изменение file mode или типа не относится к разрешённой ротации — audit отклоняет его.

Новое полное решение по CR-P4-005 **не нужно только ради checksum**, если одновременно выполнены все условия:

1. Главный чат явно утвердил именно новую редакцию управляющего документа и её полный diff; новые содержательные решения получают свои обычные approvals. Сама возможность repin не утверждает содержание будущих CR.
2. Финальная редакция зафиксирована новым управляющим commit G₂, являющимся потомком предыдущего G; baseline `76851105…`, repository/path, алгоритм сравнения и ограничения механизма не меняются.
3. Главный чат публикует новый receipt `(G₂, B₂, H₂, L₂, M)` вне DECISIONS. Codex независимо перепроверяет его и обновляет только pin, литерал P₂, соответствующее отдельное поле P4 policy и новые validation evidence. Все остальные frozen hashes/правила остаются неизменными. Предыдущий pin сохраняется в Git/evidence, но не принимается как альтернативный активный.
4. Повторяются affected scope/negative проверки и обязательная интеграционная регрессия перед принятием нового проверяемого snapshot. Результаты и pin фиксируются вне DECISIONS. Не требуется новая запись в DECISIONS только о том, что «checksum обновлена» или «этот запуск прошёл».

Отдельный новый CR/явное пересогласование потребуется при расширении разрешённых путей/версий, смене baseline, модели authority, алгоритма, ослаблении проверки содержимого/ancestry/negatives, изменении защищённых исходников/схем/зависимостей/миграций или нарушении CR-P4-001…004. Перенос истории с потерей approved ancestry также не допускается как обычный repin.

Если bytes DECISIONS не изменились и G остаётся предком нового HEAD, из-за обычного descendant commit, новой ветки или нового evidence pin обновлять не нужно. Если amended/rebased сам G, его прежний receipt недействителен: требуется новый подтверждённый commit/receipt; непрослеживаемую историю нельзя автоматически принять даже при том же H.

Таким образом, процесс не порождает бесконечные новые CR: утверждается стабильная процедура, а контрольные значения и отчёты публикуются вне контролируемого документа. Новая добровольная правка DECISIONS создаёт новую версию и один повтор процедуры, но ни один технический шаг не требует следующей правки DECISIONS. Будущая запись о закрытии Gate B, если владелец её сделает, также меняет bytes и проходит эту процедуру; это не основание объявлять Gate B закрытым сейчас.

## 9. Анализ проверяемости, риски и ограничения

1. **Цикла нет:** G сначала окончательно создан; H вычисляется после него по blob; P вычисляется после отдельного pin; ни H/G/P, ни результат прогона не надо дописывать в контролируемый DECISIONS. Новые значения сейчас честно неизвестны.
2. **Точная идентичность проверяема:** G/B/H/L/mode, ancestry, HEAD/index/disk и closed pin с независимым ожидаемым P. Нет преобразований исходных bytes или выбора «актуального main» на лету.
3. **Произвольные правки отклоняются:** контентные и path-negatives обязательны; само наличие repository context или строки APPROVED не создаёт исключения. Обновление pin только после explicit owner receipt.
4. **Защита исходников сохраняется:** все production/schema/dependency/migration inventories и hashes остаются; два изменяемых historical test-вызова проверяются отдельной точной versioned поправкой. P4-T61/T62 по-прежнему проверяют полное приложение независимо от исторического path audit, frozen/T63 не убираются.
5. **Совместимость проверена статически по текущим исходникам:** optional context сохраняет существующие singleton negative-вызовы; явная authority решает необходимость аудита copied trees; прямой pytest обходится без изменения feature-only wrapper. Реальное подтверждение после реализации — affected и полный combined прогон, не текущий анализ.
6. **Архитектура не меняется:** механизм находится только в тестах/управляющих audit данных, без runtime imports, новых зависимостей, миграций, операций или P5. Условия CR-P4-001…004 остаются в силе.
7. **Доверие к approval:** checksum доказывает совпадение bytes, а не полномочия человека. Если одновременно произвольно переписать tests, pin и ожидаемые литералы, локальный pytest не может удостоверить владельца. Граница доверия — явно полученный main-chat receipt и независимый review exact diff; криптографическая инфраструктура подписей этим CR не вводится. Нельзя называть pin-файл самоподписанным approval.
8. **Операционные ограничения:** shallow/missing/переписанная история и Git errors дают FAIL до получения настоящих объектов/решения; edits во время проверки недопустимы. Тесты идут в стабильном review checkout, pin/G/H и входные hashes проверяются до/после. Это regression audit, не sandbox против намеренно заменённого test runner или конкурентного злоумышленника.
9. **Новый управляющий commit после validation:** прежний отчёт относится к прежнему snapshot. Новый DECISIONS требует owner-approved repin и новых evidence; сохраняются оба набора. Фиксация технического pin/отчёта не требует ещё одного изменения DECISIONS.
