# CR-P4-004 — Decimal wire grammar for negative proper fractions

**Status:** APPROVED (owner-confirmed in implementation chat). **Date:** 2026-10-30. Test/contract amendment only; no new operation/type/dependency or P0/P1/P2/P3 change.

## Concrete contradiction

Approved `ENGINE_AND_OPERATION_SEMANTICS.md` defines canonical Decimal with an optional minus for a nonzero negative value, no exponent, no leading plus/zeros, and no trailing insignificant zeros. `P4_P5_HANDOFF.md` also specifies finite normalized Python Decimal and a tagged canonical decimal string. Thus Decimal('-0.25') is a nonzero negative Decimal with the natural canonical spelling '-0.25'.

But its claimed equivalent wire regex `(?:0|-?[1-9][0-9]*)(?:\.[0-9]*[1-9])?` rejects every negative proper fraction, including -0.25 and -0.001, while accepting positive 0.25. Literal implementation of that regex currently fails closed on -0.25; no rounding or substitution is performed. A valid explicit parse_number conversion can therefore produce a Decimal the proposed wire cannot represent.

## Minimal requested disposition

Approve a versioned P4 canonical-wire amendment retaining the described signed Decimal semantics, with the actually equivalent whole-string ASCII regex:

`(?:0|-?(?:[1-9][0-9]*(?:\.[0-9]*[1-9])?|0\.[0-9]*[1-9]))`

Allow -0.25 and -0.001. Continue rejecting -0, +1, leading zeros, exponent notation, 1.0/1.00, NaN/Infinity and every other noncanonical spelling. Source Decimal negative zero still canonicalizes to 0. Integer tags and all existing W/F/X fixtures remain unchanged.

Owner disposition: **"Одобрить CR-P4-004: точная signed-Decimal grammar"**, 2026-10-30. Add actual encode/decode and parse_number negative-fraction/negative-zero subcases under P4-T25/T57; retain the immutable approved ZIP and record this exact amendment separately. No new public error enum or P5 feature. Gate B still requires independent owner review.
