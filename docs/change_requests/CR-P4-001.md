## Original approved decision and conflict

The prior CR-P3-002 retained P3-T51 whole-app inventory checks for the validated P3 baseline. New explicitly approved P4 modules in `src/vde/execution/` and minimal Streamlit integration will be rejected by the historical P3 inventory while remaining legitimate under the Pilot's 12-operation whitelist.

## Approved change (strictly limited)

1. Keep **P3-T51**, its P1/P2/P3 frozen-module inventory and every negative assertion (forbidden deps, imports, services/LLM/automation/ORM, SQL changes and unapproved features). No skip, xfail, deletion or renaming.
2. Phase-scope only the obsolete P3 whole-tree assertion that would reject precisely approved P4-owned paths. Add no general P4+ exemption and do not remove original validated P3 packs.
3. Add **P4-T62 full-application audit** with explicit P0/P1/P2/P3/P4 allowlists, entire source-path/import/definition/dependency/migration inventory and negative probes against unauthorized P5+, LLM, networking, queues/workers, marketplaces, arbitrary code and new operations.
4. Record the change in a versioned P3 acceptance/traceability amendment and P4 test policy, preserve original normative docs.
5. For P4 Gate B, rerun P1 42/42, P2 54/54, P3 52/52, P4 64/64 without failures/errors/skips/xfail; record real test evidence and source-scope checks.

## Effects, risks and conditions

- Narrow test boundary only; no P0 state graph/approval semantics, no P1–P3 production runtime mutation, no database migration or extra dependencies.
- Risk: an overly broad historical exemption could miss disallowed P4 code; exact path restrictions plus P4-T62 whole-app negative probes are mandatory controls.
- Reject consequence: any legitimate P4 implementation would fail unchanged historical P3-T51 inventory, blocking Gate B.
- **Implementation not yet authorized.** Approval of this CR permits corrective *test work only after* separate explicit P4 implementation-start approval; it does not start Codex, authorize code changes or close P4 Gate B.
